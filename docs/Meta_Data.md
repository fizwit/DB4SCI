# MyDB Metadata

### mydb_admin Database
Every container that is created has metadata.
After a container is generated, metadata for the container is stored in the `containers` table.
The output of `docker inspect` is stored in a column named `data` as a `JSONB` object in PostgreSQL, in the
mydb_admin database. The `Info` key is added to the docker inspect JSON data and both the Docker
Inspect output and `Info` are stored in the `JSONB` column. Any arbitrary key/value data can be added
to `Info`.
The UI has an API for changing, adding, and updating `Info` key/value pairs.
Rows in the container table are never deleted; a complete record for every user request for
database creation is saved. If the database is created and deleted multiple times, every attempt
is saved. Use the `c_id` (container ID) field to link container metadata to the actively running
containers.

To access data for running containers, use the `ContainerState` table. The `c_id` column of all
the tables is used to join them. When a container is `deleted`, the entry in the `ContainerState` is
removed.  

### params keys
  `params` are generated by the `general_form` from
  user input. This data is used to create a container and is then stored in `admin_db`.


  Core Container/Database Information:

  - Name - Container identifier (new to version 2). `Name` must be unique across all containers.
    This allows multiple containers to use the same database name (e.g., projectA and projectA_develop
    can both have dbname="myproject")
  - service_name - Docker Swarm service name. Must be unique. Typically formatted as `mydb_{Name}`
  - dbname - Database name (not unique, can be shared across containers)
  - dbtype - Database type (Postgres, MongoDB, MariaDB, Neo4j)
  - dbuser - Database username
  - dbuserpass - Database user password
  - username - Real username from AD. dbuser can be different

  Container Configuration:

  - image - Docker image to use
  - port - Port number
  - volume_name - Docker Swarm volume name. Must be unique. Typically formatted as `mydb_{Name}`
  - config_name - Docker config file name. Must be unique. Typically formatted as `mydb_{Name}_init.sql`
  - command - Docker command to run

  Metadata/Labels:

  - owner - Owner name
  - contact - Contact email
  - support - Support information
  - description - Container description
  - manager - Manager of user (from AD)
  - department - Information from AD
  - life - Container lifecycle/lifetime DEPRECATED
  - backup_freq - Backup frequency
  - backup_window - Backup time window DEPRECATED
  - maintain - Maintenance flag DEPRECATED
  - phi - PHI (Protected Health Information) flag DEPRECATED

  Backup/Restore Related:

  - backup_type - Type of backup (e.g., 'User')
  - backup_prefix - Prefix for backup files
  - source_container - Source container for migration
  - dest_container - Destination container for migration
  - source_dbname - Source database name
  - container_name - Container name
  - Name - Alternative name field

  MariaDB Specific:

  - EAR - Encryption At Rest flag (Yes/No)

  Test/Misc:

  - con_name - Alternative container name field
  - result - Result of operation

  The most commonly used keys across the codebase are: Name, dbname, dbtype, dbuser, dbuserpass, port, image, db_vol,
  username, owner, contact, description, life, backup_freq, backup_window, maintain, phi, support, and
  port_bindings.

ADD new flag to the `Info`: `touched` which is a timestamp (TS) field. Intended to be used to check if a database is still in use and active.
